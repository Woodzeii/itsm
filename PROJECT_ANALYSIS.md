# Анализ проекта ITSM

Снимок состояния репозитория на 2026-10-08. Документ описывает код и конфигурацию, присутствующие в репозитории; наличие сущности или таблицы не означает, что для неё уже реализован рабочий пользовательский сценарий/API.

## Кратко

Проект — заготовка ITSM-системы с Angular 22 frontend, ASP.NET Core 9 backend, PostgreSQL и EF Core. Наиболее завершённые вертикальные сценарии сейчас: двухэтапный вход (проверка логина/пароля и 2FA), управление справочниками и управление классами активов/их атрибутами. Каталог услуг, заявки, SLA, согласования, уведомления, учёт активов и другие подсистемы представлены главным образом доменными моделями и схемой БД; соответствующие HTTP-сценарии в основном ещё не реализованы.

## Структура и технологии

- `frontend/`: Angular standalone-приложение, Angular Router/HttpClient, Angular Material/CDK доступны в зависимостях.
- `backend/itsm.WebApi`: ASP.NET Core Web API, контроллеры, JWT-аутентификация, OpenAPI и Scalar.
- `backend/itsm.Application`: DTO, интерфейсы сервисов и FluentValidation.
- `backend/itsm.Domain`: сущности и константы предметной области.
- `backend/itsm.Infrastructure`: EF Core/Npgsql, сервисы доступа к данным, mock LDAP, JWT/2FA, логирование email.
- `backend/itsm.Tests`: xUnit-тесты, WebApplicationFactory и тестовая инфраструктура PostgreSQL.
- `initdb/`: SQL-скрипты создания/наполнения БД; подключение каталога в Compose сейчас закомментировано.
- `docker-compose.yml`: PostgreSQL, backend и frontend.

## Frontend

Маршруты из Angular Router:

| Путь | Экран | Фактическое назначение |
|---|---|---|
| `/login` | Вход | Логин/пароль, затем одноразовый код 2FA |
| `/dashboard` | Главная панель | Демонстрационные статические числа, не загружаются из API |
| `/admin` | Главная панель | Тот же `DashboardComponent`, что и `/dashboard` |
| `/dictionaries` | Справочники | Просмотр справочников и их значений; административные операции для admin |
| `/asset-classes` | Классы активов | Просмотр классов/атрибутов, создание, активация/деактивация и удаление |

Корневой путь перенаправляет на `/dashboard`. В маршрутах не настроены guards; скрытие пунктов меню и административных действий в UI не заменяет серверную авторизацию. Страницы регистрации и подтверждения email в Angular отсутствуют.

`DictionaryApiService` и `AssetClassApiService` вызывают API напрямую. Базовые URL обоих сервисов и `AuthService` жёстко заданы как `http://localhost:5062`. Это подходит локальному Compose-порту по умолчанию, но не следует автоматически за изменённым `BACKEND_PORT` и требует настройки для другого окружения.

## HTTP API

API смонтирован через `MapControllers()`. Пути ниже реально объявлены в контроллерах. Папка `Endpoints/` не регистрируется как Minimal API: её файлы с workflow/ITAM-заголовками сейчас содержат только комментарии либо пусты и HTTP-маршрутов не создают.

### Аутентификация: `/api/auth`

Все перечисленные действия доступны без JWT:

| Метод и путь | Назначение |
|---|---|
| `POST /api/auth/register` | Валидирует запрос, проверяет уникальность логина/email, хеширует пароль, создаёт непроверенного пользователя и отправляет токен подтверждения через email-сервис |
| `POST /api/auth/confirm-email` | Подтверждает email по токену; токен действует 24 часа |
| `POST /api/auth/login` | Проверяет учётные данные через `ILdapService`, создаёт 2FA-код и возвращает `userId`/`RequiresTwoFactor` |
| `POST /api/auth/verify-2fa` | Проверяет одноразовый код и выдаёт JWT с ролями пользователя |

В текущей конфигурации `ILdapService` реализован `MockLdapService`, а не подключением к Active Directory. Код 2FA живёт 5 минут в `IMemoryCache`, одноразовый; код выводится в backend-лог. `IEmailService` зарегистрирован как `LoggingEmailService`: письмо не отправляется, токен подтверждения записывается в лог. Пароли регистрации хешируются BCrypt, но login сейчас проверяет mock LDAP, а не этот хеш.

### Справочники: `/api/dictionaries`

Контроллер требует роль `admin` или `agent` для чтения. Создание/изменение/удаление и архивирование значений дополнительно ограничены ролью `admin`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/dictionaries` | Список справочников и число неархивных значений |
| `GET /api/dictionaries/{id}` | Детали справочника со значениями |
| `POST /api/dictionaries` | Создать пользовательский справочник |
| `PUT /api/dictionaries/{id}` | Изменить имя справочника |
| `DELETE /api/dictionaries/{id}` | Удалить справочник, если он не системный и не содержит значений |
| `GET /api/dictionaries/{id}/values?includeArchived=false` | Получить значения; архивные исключаются по умолчанию |
| `POST /api/dictionaries/{id}/values` | Создать значение |
| `PUT /api/dictionaries/{id}/values/{valueId}` | Изменить имя и порядок сортировки значения |
| `DELETE /api/dictionaries/{id}/values/{valueId}` | Удалить только архивное значение |
| `POST /api/dictionaries/{id}/values/{valueId}/archive` | Архивировать значение |

### Классы активов: `/api/asset-classes`

Контроллер требует роль `admin` или `agent` для чтения. Все изменения доступны только `admin`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/asset-classes` | Список классов с количеством атрибутов и активов |
| `GET /api/asset-classes/{id}` | Детали класса и список атрибутов |
| `POST /api/asset-classes` | Создать класс |
| `PUT /api/asset-classes/{id}` | Изменить имя класса |
| `DELETE /api/asset-classes/{id}` | Удалить класс, если к нему не привязаны активы |
| `POST /api/asset-classes/{id}/deactivate` | Деактивировать класс |
| `POST /api/asset-classes/{id}/activate` | Активировать класс |
| `GET /api/asset-classes/{id}/attributes` | Список атрибутов класса |
| `GET /api/asset-classes/{id}/attributes/{attributeId}` | Получить атрибут |
| `POST /api/asset-classes/{id}/attributes` | Создать атрибут |
| `PUT /api/asset-classes/{id}/attributes/{attributeId}` | Изменить атрибут |
| `DELETE /api/asset-classes/{id}/attributes/{attributeId}` | Удалить атрибут |

В API применяются FluentValidation для ряда входных DTO, HTTP-ответы включают `400`, `401`, `404`, `409` и успешные статусы по результату операции.

## Перехватчики и фоновые обработчики

- Angular `jwtInterceptor` зарегистрирован через `provideHttpClient(withInterceptors(...))`; при наличии токена он добавляет `Authorization: Bearer ...` к каждому HTTP-запросу.
- Вебхуков (webhook endpoints) и серверных HTTP-hook обработчиков в текущих маршрутах не обнаружено.
- `SlaBreachNotifier.cs` содержит только комментарий-заголовок; он не является рабочей фоновой задачей и не зарегистрирован как hosted service.
- `ExceptionMiddleware.cs` пуст и не подключён в pipeline.
- Файлы `Endpoints/WorkflowEngine`, `TicketManagement`, `AssetManagement`, `Configuration` содержат в основном комментарии-заготовки. `AccessManagement/RequestAccess.cs` пуст; файлы согласования содержат только комментарии.

## Доменная модель и БД

`ItsmDbContext` и миграции описывают следующие области:

- Пользователи, роли, сопоставления ролей, группы специалистов, арендаторы, аудит входа и парольные политики.
- Каталог услуг, шаблоны форм, поля и видимость полей по ролям.
- Заявки: типы/статусы и переходы, критичность, согласования, сообщения, вложения, аудит, связи с активами и релизами.
- SLA: политики и значения, рабочие графики/часы, исключения календаря, правила назначения, эскалации и уведомления.
- ITAM: активы, классы активов и динамические атрибуты, перемещения и журнал истории.
- Справочники и значения.

EF Core настроен на PostgreSQL/Npgsql, для JSON-схемы формы используется `jsonb`; присутствуют миграции и `ItsmDbContextFactory`. Сервисы с реальной CRUD-логикой в Infrastructure сейчас есть для справочников и классов активов/атрибутов, а также пользователей и регистрации. Большая часть остальных наборов сущностей сама по себе не подтверждает наличие бизнес-обработчиков.

## Запуск и конфигурация

- Compose поднимает PostgreSQL 16, backend и frontend; PostgreSQL доступен с хоста на порту `5433` по умолчанию, API на `5062`, UI на `4200`.
- Compose читает `backend/.env`. Этот файл не включён в документ; не публикуйте секреты из `.env`.
- Backend требует строку `ConnectionStrings__DefaultConnection` либо переменные `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`; JWT key обязателен.
- В Development API включает OpenAPI/Scalar и запускает `DatabaseSeeder`, если в БД ещё нет пользователей. Seeder не создаёт схему и не вызывает `Database.Migrate()`.
- Подключение `./initdb` в Compose закомментировано. Поэтому свежий том БД требует отдельного применения миграций/SQL-инициализации; не следует считать, что схема создаётся автоматически.
- Для production email/LDAP нужны реальные реализации вместо текущих dev/mock-сервисов. 2FA через код из логов и dev-пользователи не являются production-механизмом.

## Тесты

В `backend/itsm.Tests` присутствуют тесты аутентификации и регистрации, тесты `ItsmDbContext`, email-инфраструктуры и обработчика создания заявки; используются xUnit, Moq, WebApplicationFactory и Testcontainers PostgreSQL. Этот обзор не запускает тестовый набор, поэтому статус прохождения тестов здесь не заявляется.

## Основные пробелы реализации

1. Нет реализованных API/экранов для полного жизненного цикла заявок, каталога услуг, SLA, согласований и активов, несмотря на наличие соответствующих сущностей.
2. Нет реального LDAP/почтового провайдера; 2FA-код и токен email попадают в логи.
3. Нет guards на UI-маршрутах, конфигурация API URL зафиксирована на localhost, а `/admin` ведёт на обычную dashboard-страницу.
4. Миграции БД не применяются автоматически при старте Compose; initdb volume отключён.
5. `Endpoints/`, SLA notifier и exception middleware — заготовки, а не активные обработчики.
